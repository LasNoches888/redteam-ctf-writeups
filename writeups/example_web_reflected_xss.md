# Reflected XSS в поиске — web — 100 (учебное задание)

> Практика на собственном стенде [`redteam-vulnerable-webapp-lab`](https://github.com/LasNoches888/redteam-vulnerable-webapp-lab),
> запущенном локально (`docker compose up -d`, `http://localhost:5000`).

## Описание
Страница `/search?q=…` показывает искомую фразу. Нужно проверить, безопасно ли выводится пользовательский ввод.

## Разведка
1. Обычный запрос: `http://localhost:5000/search?q=test` → заголовок «Результаты для: test».
2. Значение параметра `q` попадает в ответ. Проверяем, экранируется ли HTML:
   `http://localhost:5000/search?q=<b>test</b>` → слово `test` отображается **жирным**. Теги не экранированы — HTML интерпретируется браузером.
3. Смотрим исходный код ответа (`curl -s 'http://localhost:5000/search?q=<i>x</i>'`) и видим `<h1>Результаты для: <i>x</i></h1>`
   без преобразования `<` в `&lt;`.

## Эксплуатация
Подставляем скрипт-«пробник», который безвреден, но доказывает выполнение JavaScript:
```
http://localhost:5000/search?q=<script>alert(document.domain)</script>
```
При открытии ссылки в браузере появляется окно с доменом — код выполнился в контексте приложения.

Реальный сценарий атаки (описание для понимания риска): злоумышленник отправляет жертве такую ссылку; скрипт получает доступ
к cookie без флага `HttpOnly`, DOM страницы и может выполнять действия от имени пользователя.

## Результат
Уязвимость подтверждена: пользовательский ввод выводится как HTML без экранирования (CWE-79).

## Выводы / защита
1. **Экранировать вывод** по контексту: HTML, атрибут, JavaScript, URL. В Python — `markupsafe.escape(q)` или шаблонизатор
   с автоэкранированием (Jinja2 с `{{ q }}`).
2. **Content-Security-Policy**: запретить встроенные скрипты (`script-src 'self'`) — вторая линия защиты.
3. **Cookie** с флагами `HttpOnly`, `Secure`, `SameSite`.
4. Валидация входных данных — дополнительная мера, но не замена экранированию.

Исправленный вариант — в `redteam-vulnerable-webapp-lab/app/app_fixed.py`.
